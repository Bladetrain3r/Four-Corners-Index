# G6 evidence: the live pipeline (2026-09-30)

**Claim:** the daily and Pages workflows exist, validate, and the commands they run pass locally the way the workflows run them; a forced source failure turns the run red, names the source in an issue, and the site shows the last good date; a simulated 15th-of-month publication appends ledger lines and the verifier passes. What could only be proved on GitHub is listed last.

## Files
- `.github/workflows/daily.yml`: cron `17 5 * * *` and manual dispatch (with a `force_fail` input); restores the raw snapshots (committed archive, then the monthly Release assets, `--partial`); `python -m pipeline.daily`; `python ledger/verify.py ledger/index.jsonl`; packs new raw snapshots and uploads them to the `raw-YYYY-MM` Release; commits `data/` and `ledger/` if anything changed; opens or comments on an issue named `Source failing: <source>`; turns the run red; then calls `pages.yml` even when a source failed, so the site shows the failure.
- `.github/workflows/pages.yml`: on push to `main`, on call, on dispatch; `python -m pipeline.publish --out site`; the static and data-contract tests on the result; official Pages actions.
- `pipeline/daily.py`: per-source fetch and parse (a failing or reshaped source never stops the others and is rebuilt from its last good snapshot), `data/health.json` (status, last good date, failing since, redacted message), the issue text, the 15th rule (`cap_month`), the simulation. `pipeline/build.py` takes `max_month`; `pipeline/snapshot.py` gained `record`, `--partial`, `--pack-new --since`.

## Evaluations run
1. **YAML and commands** (`tests/test_workflows.py`, 10 tests, also in CI): both files parse; actions are pinned to a major version; permissions are the minimum each needs; secrets appear only in `env:` and are never echoed; every `python -m pipeline.X` in a workflow imports, has `main`, and accepts every flag the workflow passes; the archive and `ledger/verify.py` it names exist. Mutation check: misspelling `--force-fail` in `daily.yml` turns the test red.
2. **Entrypoints run locally the way the workflow runs them** (same test file): `python ledger/verify.py ledger/index.jsonl` (420 lines, 0 problems); `python -m pipeline.snapshot --restore snapshots/raw_2026-09-29.tar.gz --partial`; `--pack-new ... --since <manifest>` writes nothing when nothing is new; `python -m pipeline.publish --out site` and the static tests (G5).
3. **A real live run** (`python -m pipeline.daily --dry-run`, in a temporary copy): all 19 requests from the six sources fetched and parsed; 2 changed (`ember/prices_monthly`, `ember/prices_daily`, both revised upstream since the archive) and 0 ledger lines were added because no published index value changed at six decimals; nothing in the repository changed. `data/health.json` is committed with all six sources ok, last good 2026-09-30, from that run.
4. **Failure path.**
   - Offline (`tests/test_daily.py`, 8 tests): a forced `eia` failure gives `failing_sources = {eia}`, the other five stay ok, the build still runs from eia's last good snapshot, `finish()` returns 1 and writes the issue file (`Source failing: eia`, the source's section, last good and failing-since dates); a reshaped response (HTML instead of the Eurostat file) fails the source and is never stored; a key inside an error message is redacted before it reaches the health file or the issue; failing since is kept across days and cleared on recovery; an unchanged run adds no snapshot and no ledger line and gives a byte-identical health file.
   - Live, through the CLI: `python -m pipeline.daily --dry-run --force-fail eia --issue-file ...` exited 1, printed `WOULD OPEN ISSUE (dry run): Source failing: eia`, and wrote an issue naming eia's four requests, with `last good: 2026-09-30`.
   - The site (`tests/test_site_browser.py`, screenshot `evidence/G5/failing_source_banner.png`): with eia failing, every page shows a banner naming eia with its last good and failing-since dates, the footer says `1 of 6 sources failing`, and the Sources page shows the notice beside eia and "fetched and parsed fine" beside the others.
5. **Simulated 15th** (`python -m pipeline.daily --simulate-publication`, offline, in a temporary directory): a ledger built through 2026-07 as on 2026-08-15 has 278 lines; on the simulated 2026-09-15 the newest month is published and **two lines are appended, one per index**: retail 2026-08 **provisional** 0.157277 USD/kWh and wholesale 2026-08 **final** 0.149556; the 278 earlier lines are byte-identical; `ledger/verify.py` says `280 lines, 0 problems, chain intact`. The appended values equal the committed ledger's own (test asserts it), so nothing was invented. Before the 15th the newest publishable month is the one before (`cap_month`, tested at month and year ends).

## Result
220 tests pass locally (10 workflow, 8 daily, 17 browser, 13 static); ruff clean; tracked repo 21.5 MB; the generated site is 13 MB.

## Not proved, stated plainly
A real dispatch needs the workflows on the default branch, so all of these are unproved until Ziggy merges:
- the cron trigger, and that `workflow_dispatch` shows the `force_fail` input;
- `secrets.EIA_API_KEY` reaching the run (the name is in `reports/SETUP.md`; whether it is set on the repository is not visible to the builder);
- that GitHub-hosted runners can reach all six sources (they were reached from this build environment through its proxy; a source that blocks datacentre addresses would show up as a red run and an issue);
- that `GITHUB_TOKEN` may push to `main` with the `permissions:` in the file (a repository setting, "Workflow permissions", or branch protection may refuse it: Ziggy's to change, never the builder's);
- Release creation, upload and the restore-from-Release path (`gh release ...`): the pack, the partial restore and the manifest check are tested, the `gh` calls are not;
- issue creation, and the search that avoids duplicate issues;
- the reusable-workflow call from `daily.yml` to `pages.yml`, and the Pages deploy itself (Pages must be switched on first: Settings > Pages > Source: GitHub Actions).
Also: a daily commit of `data/health.json` (its last good date changes each day) is a deviation from "an unchanged source produces no commit": the source data does not change, the health record does. It is one small file; the alternative (not committing it) would lose the last good date.
