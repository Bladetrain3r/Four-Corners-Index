# G8 evidence: the feedback button (2026-10-09)

**Idea (Ziggy):** a thumbs-up/thumbs-down choice, an optional comment and an optional reply-to email. **Decisions (Ziggy):** the receiver runs on his own always-on EC2 instance; the email is optional and used only to reply.

## What was built
- `feedback/server.py`: a standard-library-only receiver (one POST endpoint, `/healthz`, `serve`, `prune`, `report`), with `feedback/README.md` and `feedback/deploy/` (systemd unit with hardening, prune timer, Caddy file for HTTPS, env example).
- `site/js/feedback.js` and a footer block on every page: two vote buttons (real buttons with `aria-pressed`), a labelled comment box, a labelled email field, a hidden honeypot, a status line, and the privacy sentence (what is kept, for how long, why, which host it goes to, whom to ask).
- `data/manual/feedback.json` (`endpoint`, `contact`, `retention_days`), checked by `pipeline/site_feedback.py` and published in `meta.json`. **The form is hidden until both `endpoint` and `contact` are set**, so merging this changes nothing for visitors until Ziggy has the endpoint up.

## What it keeps and what it never keeps
Kept: the vote, the page path, a received time, a random id, and (only if typed) a comment and an email. Never: an IP address, a user agent, a cookie, a referrer. The access log has method, path and status only. `prune` deletes comment and email after N days (default 90, which the visitor is told) and keeps the vote.

## Evaluations run
- **Receiver over real HTTP** (`tests/test_feedback_server.py`, 15 tests): a valid vote is stored with exactly the expected fields; comment and email optional, empty strings count as absent; 14 malformed bodies refused with a reason and nothing stored (bad vote, wrong version, unknown field, foreign page URL, over-long page and comment, control characters, bad emails including a header-injection attempt); a filled honeypot is answered as success and dropped; body size, content type and invalid JSON are enforced; a foreign origin is refused (403) and a preflight is answered only for the site; other paths 404; the rate limit works per client with `Retry-After`, ignores a spoofed `X-Forwarded-For` unless behind the trusted proxy and then keys on the proxy's own entry, and the daily limit applies after the hourly one; the store is mode 0600 and append-only; `prune` redacts only entries past retention and keeps the vote; `report` hides comments and emails unless asked; mail has a safe subject and a Reply-To, and a failing mail never loses the entry; **no address and no message text reaches the log**.
- **Settings** (`tests/test_feedback_config.py`): the committed configuration is off; a complete one gives the page what it needs; 11 unsafe or half-set configurations fail the build (http, wrong path, a query string, credentials in the URL, an IP address, retention out of range, a missing contact); the receiver imports only the standard library; the widget has one `fetch`, `credentials: "omit"`, `referrerPolicy: "no-referrer"`, no storage, no cookies, no beacon; the prune timer's days equal the site's `retention_days`.
- **In a browser against a real receiver on a second port, so CORS is exercised for real** (`tests/test_site_browser.py`): with no endpoint, no form on any page; with one, **the page contacts no host but its own until Send is pressed, then exactly one more**; Send is disabled until a vote; a vote, a trimmed comment and an email arrive in the store with the right page; a vote alone is enough; a bad email blocks the send with a message and sends nothing; a dead receiver gives "could not be reached" and keeps the visitor's text; a rate-limited sender gets "sent a few already"; the form works by keyboard (Space on a vote), the honeypot is never reachable by Tab, no horizontal scroll at 390 px. Screenshot: `evidence/G5/feedback_phone.png`.
- A manual run of the real command line: `serve`, a post by curl, the log (no address), the file mode (600), `report`, `prune --days 0`.

## Not proved, stated plainly
- **Nothing here has run on the EC2 instance, behind Caddy, with a real certificate or with SES.** The systemd and Caddy files are written to the README's steps but untested; the first real deployment is Ziggy's, and the README lists a check at each step.
- A custom domain is needed for the receiver's HTTPS name; a bare IP will not work in a browser.
- **Privacy is a design, not a legal opinion.** Ziggy is the responsible party (POPIA; GDPR for EU visitors). The form says what is kept and whom to ask; the `contact` he sets must be answered.
- The honeypot and rate limit stop casual bots, not a determined one; the worst a flood can do is fill the file (the body limit and the hourly limit keep that slow). A CAPTCHA was left out on purpose (a third party and a tracker).
