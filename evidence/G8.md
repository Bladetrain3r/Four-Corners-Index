# G8 evidence: the feedback button (2026-10-09), as finally built

**Idea (Ziggy):** a thumbs-up/thumbs-down choice and a comment. **Reversed decision (Ziggy, same day):** "make the button direct to the Issues page. Four corners should not need an active webhost backend."

## What was built, and what was dropped
- **Built:** two links in the footer of every page, "👍 Useful" and "👎 Not useful", opening a pre-filled GitHub issue form (`.github/ISSUE_TEMPLATE/feedback-up.yml`, `feedback-down.yml`, `config.yml`). The title carries the vote, the `page` field is filled in from the page the visitor was on (path and query, so a region page names its region), and the comment is optional, so a bare thumb is a complete answer. A third link goes to all issues. `site/js/feedback.js` only builds the two URLs: no form, no `fetch`, no storage, no cookie.
- **Dropped:** the stdlib receiver for the EC2 box, the settings file and its checks, the email field and the retention timer. They were built, tested (309 tests) and pushed at `297e686` on the branch `claude/optimistic-gates-u7dyq8` and removed in the commit after it: `git show 297e686:feedback/server.py` and `git checkout 297e686 -- feedback/` bring them back for Ziggy's own hosted services (the README there lists the deployment steps).

## Why this is better for this site
- The site stays a static page with **no live backend**: nothing to host, patch, certificate-renew or secure, no public write endpoint to abuse, and the "no request to any host but its own" property is exact again (no exception for a feedback host).
- **Less personal data:** we collect no email or other details; GitHub holds the submitter's identity under its own terms. The reply goes on the issue thread, and spam is GitHub's to moderate.
- The cost, stated: feedback is **public** and needs a **GitHub account**, and a visitor who has none cannot send any. The footer says so before the click.

## Evaluations run
- `tests/test_feedback_links.py`: both issue forms parse; titles start with their emoji; only prefillable field types (`input`, `textarea`, `markdown`); the ids are exactly `page` and `comment`; the comment is optional; each form warns that the issue is public and asks for no personal details; the templates the script names exist; the script has no `fetch`, `XMLHttpRequest`, `sendBeacon`, storage, cookie, `FormData` or `POST`; the receiver and its settings are gone from the source tree.
- Browser, on 7 pages (`tests/test_site_browser.py`): the page contacts no host but its own on load; the two links go to `https://github.com/Bladetrain3r/Four-Corners-Index/issues/new` with the right template, a title carrying the vote and the page, and `page` equal to the visitor's page (checked against `region.html?r=EU`); `target=_blank` with `rel` containing `noopener`; the privacy sentence ("public", "no email") is there; the links are reachable by keyboard, 44 px tall, and the page does not scroll sideways at 390 px. Screenshot: `evidence/G5/feedback_phone.png`.
- Whole suite: see `LOG.md` R32.

## Not proved, stated plainly
- **The prefill on GitHub itself was not seen.** GitHub's documentation says form fields are prefilled from the URL by field id and the `title` parameter is honoured; it does not document dropdown prefill, so there is none. I could not open github.com's form from the build environment, so the first real click is the test: if the page field comes up empty, the title still carries the page.
- **Labels:** the forms ask for a `feedback` label, which only applies if that label exists in the repository (Ziggy creates it once, or it is silently skipped). I did not create it: labels are repository state, not code.
- Issues must stay enabled on the repository (they are today).
